# 第三版第一轮内容策划

日期：2026-10-23。目标：让首页的精选、文章库的检索、项目页的说明和正文的连续阅读各自承担明确任务。

## 真实内容盘点

本轮通过本机MySQL只读查询元信息，未读取草稿正文、未写入数据。详细标题/状态清单保存在被Git忽略的 `artifacts/design-v3/content-inventory.private.json`，样稿服务无法访问该文件。

| 内容 | 当前数量与状态 | 本轮处理 |
| --- | --- | --- |
| 文章 | 7篇：3篇PUBLISHED、4篇DRAFT；回收0篇 | 只盘点。3篇公开文章是否继续作为正式展示，后续由用户逐篇决定 |
| 资源 | 共4项数据库记录 | 不把记录总数当公开资源数，后续按可见状态与用途筛选 |
| 分类 | 2项 | 正式专题应结合实际文章，避免仅改分类名称就称为学习路径 |
| 第二版录入的正式稿 | 编号5、6、7仍为草稿范围；内容状态见已有录入记录 | 保留未公开状态，不把正文放进样稿、Git或预览附件 |
| GitHub项目 | 既有公开快照7个仓库，含1个fork | 样稿保留全部仓库，精选区域不替代完整列表 |

## 首页的内容顺序

1. **作者定位**：保留firefly1v、萤火手记与Java/前端实践方向；新标题提案为“把问题弄明白，把思考留下来”。无需头像、学历或工作经历才能成立。
2. **精选文章**：先只放一篇完整且有代表性的文章，展示摘要、栏目和阅读时长。正式首批可考虑从现有草稿中选择“网站动机”或“备份恢复”，经用户审阅并明确发布后再采用。
3. **学习路径**：用3篇确有连续关系的内容构成“从请求到交付”。当前样稿是演示专题；真实文章尚不齐全时，首页应隐藏或改为普通主题入口，不显示虚假的“已完成”。
4. **最近记录**：使用紧凑文字列表，突出标题和摘要。正式实现按公开日期读取真实文章，不手工伪造活跃度。
5. **项目入口**：PersonalWebsite2优先，其次starticket和dsh-recheck；侧栏只给简短入口，项目页展开说明。

本轮暂不加入访客数、点赞数、虚构项目成果、空白联系方式或大量装饰模块。

## 四类页面的内容职责

| 页面 | 放什么 | 用户完成什么操作 |
| --- | --- | --- |
| 首页 | 作者定位、精选、学习路径、近期文章、项目入口 | 选择一篇值得开始的内容 |
| 文章库 | 栏目、标签、专题、检索、卡片/紧凑列表、分页 | 找到具体问题对应的笔记 |
| 项目 | 一个重点案例、全部公开仓库、可筛选更新链 | 理解项目用途，再查看源码和相关记录 |
| 阅读 | 摘要、章节、图文/代码、目录、阅读偏好、专题下一篇 | 连续读完并返回原列表或继续下一篇 |

## 样稿文章清单

以下8篇是专为界面设计新写的演示内容，标题、日期、阅读时长、专题关系和正文均不能视为作者已发表的文章。日记也是虚构的排版样例，不代表用户经历。

| 示例 | 栏目/标签 | 覆盖的设计情况 |
| --- | --- | --- |
| 一条请求，怎样抵达数据库 | 笔记 / Java | 首页精选、请求路径图、正文关键词“事务” |
| 一份备份，什么时候才算可靠 | 笔记 / MySQL | 数据类封面、专题收尾、代码复制 |
| 用状态图说清楚一次业务流转 | 笔记 / Java | 状态图、正文关键词“幂等” |
| 把零散问题，写成可以重用的笔记 | 心得 / 写作 | 非代码类内容、写作专题 |
| 页面变窄之后，什么应该先留下 | 笔记 / Vue | 屏幕示意图、专题中间篇 |
| 把屏幕关掉，出去走一小段 | 日记 / 日常 | 短摘要与日记筛选 |
| 当一次请求没有按预期完成：从错误提示、重试入口到保留输入的界面细节 | 笔记 / Vue | 长标题、无自定义封面回退 |
| 给一次版本交付留一张检查表 | 心得 / 交付 | 第二页、写作专题终篇 |

演示正文重在展示章节、段落、图例与代码的排版，内容深度不代表正式文章质量。第二版结构对照与第三版从同一份8篇数据读取，不以数据丰富程度制造差异；对照仅模拟结构，非第二版业务页面的精确截图。

## 项目案例采用规则

| 项目 | 当前可写 | 正式案例待补充 |
| --- | --- | --- |
| PersonalWebsite2 | 当前工作区能核对的技术栈、文章与写作流程、媒体、备份恢复；已有版本记录 | 用户希望强调的学习收获、本人手敲与工具协作边界、愿意公开的项目截图 |
| starticket | 公开仓库简介中声明的票务业务方向 | 独立验收结果、本人贡献与设计取舍；不能把README声明改写成已独立验证的成果 |
| dsh-recheck | 公开仓库简介中声明的证据复核工具用途 | 使用场景、本人工作与示例截图 |
| 其余非fork仓库 | 仓库名称、简介、语言及公开链接 | 个人贡献说明和适合作为案例的程度 |
| floating-ui | fork身份、仓库简介、公开链接 | 本人改动的可核对范围；不得将上游库写成本人的原创项目 |

样稿只使用当前公开快照，未声称逐一运行所有外部项目。项目弹窗将“可核对内容”与“待补充案例”分开；未来用户补充材料时再完善事实。

## 效果确认后需要决定的事项

- 是否接受紧凑首页、独立文章库、项目独立页面，以及当前文字密度。
- 是否采用新首页标题；现有正式介绍仍保持原样，本轮提案未写回siteProfile。
- 首批公开哪篇已录入草稿、是否撤回旧测试文章，需要逐篇明确；确认样稿不等于授权发布草稿。
- 若希望加入个人照片、作品截图或其他联系方式，再提供愿意公开的材料。资料不足时继续使用字母f和原创矢量封面。

下一轮业务接入再讨论具体表结构与兼容迁移。本轮不新增数据库表，也不把样稿hash路由直接替换正式Vue Router。
