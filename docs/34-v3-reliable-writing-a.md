# 第三版4A：编辑冲突检测与编辑稿隔离

日期：2026-10-25。基线：`2714be2` / `v3.0.0-alpha.2`。本轮已实现并完成隔离验收，尚未发布；构建版本暂沿用alpha.2。个人库尚未执行008，启动本轮后端前需要完成下面的升级步骤。

## 本轮行为

| 操作 | 管理端 | 访客 |
| --- | --- | --- |
| 新建/保存草稿 | 保存内容，可继续编辑 | 不可见 |
| 保存已公开文章 | 保存独立编辑稿，提示“公开版本尚未更新” | 继续看到上次公开版本 |
| 发布修改 | 先保存本窗口内容，再用该版本明确发布 | 内容、分类标签、封面与图片关联一起更新 |
| 另一窗口已修改 | 返回412，保留输入和原版本，不自动重试覆盖 | 不受这次失败操作影响 |
| 撤回/回收 | 保留文章及编辑稿 | 文章和仅由它公开的本站图片不可见 |
| 从回收站恢复 | 保留编辑稿，恢复为非公开草稿 | 明确发布前仍不可见 |

发布保留第一次发布时间。标题、摘要、Markdown正文、栏目、分类、标签关联、封面、置顶及正文本站图片关联均随编辑稿保存，发布前不改变公开查询。分类/标签**名称重命名**仍是原有的全站共享维护操作，会影响所有引用该名称的文章；它不属于文章编辑稿。

“有待发布编辑稿”表示存在独立保存的稿件，不是逐字差异比较；保存完全相同内容也会生成编辑稿并推进版本。本轮不自动保存，不记录修订历史，不把输入写进浏览器存储。刷新/关闭前仍需手动保存；未保存提醒不能替代备份。

## 升级本机数据库

本轮验收只操作独立测试库，**没有替你对 `personal_website` 执行008**。以下操作用于把个人环境切换到本轮代码。

1. 停止使用该库的后端及其他写入任务，关闭旧管理端窗口。旧前端不发送版本条件，不能混用。
2. 在项目根目录做完整离线备份；已有备份目录不能重复使用，换一个新的名称：

   ```powershell
   python scripts/local-backup.py backup --offline --backup E:/PersonalWebsite2/backups/before-008-personal
   ```

   使用实际媒体目录配置，不要指向空目录代替现有图片。该备份包括数据库、媒体、当前源码及本机配置，留在已忽略的backups目录。

3. 在IDEA数据库控制台先核对目标和现有结构：

   ```sql
   USE personal_website;
   SELECT DATABASE();
   SHOW COLUMNS FROM article LIKE 'write_version';
   SHOW TABLES LIKE 'article_edit%';
   ```

   从alpha.2升级时，后两项应均无记录。若已有部分结构，先检查迁移执行情况，不要盲目重跑。

4. 打开并执行一次 `E:\PersonalWebsite2\database\008-article-editing.sql`。它增加一个版本字段和三张编辑稿表，不改旧文章内容或发布状态。MySQL的DDL不是整份脚本的可回滚事务；报错后停止，不要继续启动应用或重复整份脚本。
5. 执行下面的验收SQL：

   ```sql
   SHOW COLUMNS FROM article LIKE 'write_version';
   SHOW TABLES LIKE 'article_edit%';
   SELECT COUNT(*) AS editing_rows FROM article_edit;
   SELECT COUNT(*) AS nonzero_versions FROM article WHERE write_version <> 0;
   ```

   刚升级且尚未启动写入时：版本字段为BIGINT、非空、默认0；显示 `article_edit`、`article_edit_tag`、`article_edit_media` 三张表；两个COUNT均为0。总业务表数从8变为11。
6. 应用账号需要新表的SELECT/INSERT/UPDATE/DELETE权限。若原先按整个库授权，无需扩大权限；不要给应用账号DDL或其他库权限。
7. 同步启动本轮前后端并重新登录。先选择测试文章验证“保存编辑稿不更新公开文 → 发布修改后更新 → 两窗口旧版本保存被拒绝”。不要用不愿公开的日记做发布测试。

新安装依次执行000～008。升级失败需要恢复时，使用离线备份工具先恢复到全新的 `pw_media_restore_` 专用库并核对内容，再安排切换；回退到alpha.2必须同时恢复对应的升级前数据并使用旧版代码，不能只回滚代码后继续写入已有编辑稿的库。

## 冲突处理

遇到412时，不会将你的内容覆盖为服务器稿，也不会刷新版本后偷偷重试。

1. 本地标题和正文仍可选择、复制。先保留需要合并的修改。
2. 点击“查看服务器版本（保留当前输入）”，展开服务器标题、摘要和只读正文进行对照。这一步不修改本地稿或版本号。
3. 点击“重新加载服务器版本”时，存在未保存修改会再次出现放弃确认；取消则继续保留输入。
4. 确认重新加载后，在最新稿件上手动合并需要的内容，再保存。没有自动合并或强制覆盖入口。

服务器对照是点击时的快照，另一个窗口还可能继续写入；后续操作仍通过版本检查保护。回收、撤回、恢复和发布同样检查版本。

## 接口及数据流

管理端详情、列表和写入响应增加 `version`，详情/列表另含 `hasUnpublishedChanges`。现有文章的版本初始为0，每次成功保存或状态写入递增。新建POST不要求版本。

已有文章的PUT、DELETE及POST publish/unpublish/restore必须携带读取时得到的版本，例如：

```http
If-Match: "3"
```

缺少条件返回428；格式非法返回400；版本落后返回412；已回收文章的保存/发布/撤回仍返回409。认证和CSRF继续要求。先锁定文章行再比较版本，保存/发布全过程处于同一事务；发生校验错误时编辑稿、关联和版本一起回滚。

`article`及原标签/媒体表保留基准副本（新文章最初是非公开草稿；公开后即为公开副本）。首次后续保存按需建立 `article_edit` 及独立标签/媒体关联。管理端优先读取编辑稿；所有访客查询与图片权限只读取原公开副本。发布时复制编辑稿及关联、更新版本与状态、删除已发布的临时编辑稿；外键级联只清除编辑稿关联，不删除文章或媒体文件。

新表由现有整库备份自动覆盖，未新增备份工具。已在隔离环境验证旧八表升级后原字段/数据一致，以及包含公开稿、待发布稿、版本、标签、媒体关联和两张图片的11表完整恢复。

涉及文件：`AdminArticleController.java`、`ArticleTags.java`、`MediaStore.java`、后台编辑/列表页面、`adminSession.js`及008迁移。旧文档中不带版本条件的文章写入示例，以及“保存会立即公开”的说明，在本轮代码中以本节为准。
